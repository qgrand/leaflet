## What

**Per Sconl: option (a).** Reimplement `doc-builder`, `registry`, `node-tree`, `naming`, `style` and the 10 archetype modules' logic as native Rust, matching the JS engine's behavior field-for-field rather than translating its code line-by-line. `render-markdown`/`render-html` are low-risk (string templating, no exotic crate needed). `render-docx`/`render-pdf` are the real work: **no vetted Rust equivalent exists yet in this codebase** — evaluate and pick real crates (`docx-rs`-class for `.docx`, `printpdf`-class for `.pdf`) as part of this row, not before it. **Do NOT port:** `generated_docs.tsv` indexing, OneDrive push/browse, `tasks.tsv` binding, engagement/venture resolution — those stay in iSconl and arrive over the API as a resolved payload. **Two inherited rules are non-negotiable:** `.docx` is built programmatically, never by templating into an existing Word file; `.pdf` is built directly from the node tree, never converted from the `.docx`. **And no AI anywhere in the generation path** — AI may fill an individual field on request, never author a document. **Race to fix on the way in:** iSconl allocates document IDs as `SB%04d` by scanning existing rows for the max numeric suffix, which races under concurrent generation. Qpress must not inherit that. **Acceptance bar, since fidelity is the real risk here:** for at least one archetype per renderer format, generate from the same input via both the JS engine (iSconl `scope`) and the new Rust engine, and diff the actual rendered output (text content for `.docx`/`.pdf`, not byte-identical binaries) before calling any archetype done.
